# Artifact Admission

Artifact Admission is a dependency-free, local Node.js gate for teams that need an explicit **admit or deny** decision before an implementation artifact enters a governed stage.

It checks a declarative policy against a workspace, an exact subject digest, required evidence files, and one unambiguous lifecycle receipt. Any missing, malformed, stale, future-dated, mismatched, ambiguous, or path-escaping input denies admission.

## What it is for

- promoting an implementation from review to an approved internal stage;
- enforcing exact artifact and evidence hashes in a repository or offline bundle;
- rejecting stale or ambiguous verification receipts;
- leaving a structured, receipt-digest-bound JSON decision record for CI, agents, and reviewers.

## What it is not

Artifact Admission does not create or verify cryptographic signatures, prove build provenance, scan an artifact for vulnerabilities, establish that evidence is correct, or guarantee fitness for use. It is designed to complement systems such as SLSA provenance, Sigstore/GitHub artifact attestations, in-toto, and policy engines—not replace them.

## Quick start

Requires Node.js 20 or newer.

```sh
npm test
node src/cli.mjs verify \
  --policy examples/valid/policy.json \
  --root examples/valid/workspace
```

The bundled receipt can be regenerated by the synthetic verifier with a fixed timestamp:

```sh
node examples/valid/synthetic-verifier.mjs \
  examples/valid/policy.json \
  examples/valid/workspace \
  receipt.json \
  2026-09-27T18:10:00Z
```

The command exits `0` only for `ADMIT`, `1` for a policy denial, and `2` for invalid invocation or an unexpected runtime failure.

Install the exact v0.1.1 first-party release package in another local project:

```sh
npm install https://kaldenframelabs.com/downloads/kaldenframe-labs-artifact-admission-0.1.1.tgz
```

This direct package path does not claim npm-registry availability. GitHub may be added as a source and release mirror.

Calculate a SHA-256 digest for policy preparation:

```sh
node src/cli.mjs hash examples/valid/workspace/dist/application.txt
```

Write an admission decision atomically:

```sh
node src/cli.mjs verify --policy policy.json --root workspace --output decisions/release.json
```

Output is create-only. The CLI refuses to overwrite an existing path or write into the configured receipt directory, policy, subject, required evidence, or deny-marker paths.

## Fail-closed checks

1. Policy schema and portable identifiers are valid.
2. Every configured path uses a portable forward-slash relative form and remains contained by the resolved workspace root after symlink resolution.
3. The subject file exists and matches the policy SHA-256.
4. No configured terminal deny marker exists.
5. Every required evidence file exists and matches its policy digest.
6. The receipt directory contains no malformed, duplicate-key, oversized, or path-escaping JSON receipts and remains within a 200-file bound.
7. Exactly one receipt matches the subject digest, path, policy ID/version, stage, and receipt kind.
8. The receipt state is allowed, its timestamp is neither stale nor in the future, and its verifier name, version, and exact source digest match an allowed policy identity.
9. The selected receipt binds every required evidence digest.

The v1 decision record always repeats the product boundary so downstream users do not confuse a local consistency decision with a security guarantee. It also records the exact SHA-256 of the selected receipt bytes. Evaluation is deterministic when inputs and the evaluation clock are fixed; ordinary CLI runs intentionally record the current time.

Machine-readable JSON Schemas for policies, receipts, and decisions are included in `schemas/`.

## Operational assumptions

- Run against a quiescent or immutable workspace; this process does not create a filesystem snapshot or lock files against concurrent changes.
- Receipt freshness depends on the local system clock, so CI runners should use a trustworthy synchronized clock.
- Treat the policy file and its allowed verifier identities as trusted configuration and protect them with the same controls as the stage they govern.

## Privacy and network boundary

The library and CLI perform no network requests. They read the policy and workspace paths supplied by the caller and write a decision only when `--output` is used.
